시연 1 · 숙려 리스트

담아 두고, 며칠 뒤 다시 묻는다

  • 상품명·가격·이유·숙려 기간(1·3·7일, 직접 입력 1~30일)
  • 종료 시각 = 등록 시각 + 일수 × 24시간. 정각부터 "재검토 가능"
  • 처음 적은 이유를 보여주고 "아직 필요한가요?"
  • 구매함 · 구매 포기 → 결정 기록. 숙려 중에도 결정 가능
  • 이 브라우저에만 저장. 손상되면 덮어쓰지 않고 확인 후 초기화

시연: "예시 물건 넣기" → 재검토 가능 카드에서 구매 포기 → 결정 기록 확인 → 새로고침

바이브 코딩에서 겪은 일 1

테스트가 잡은 버그: "총지출이 큰 쪽"을 거꾸로 표시

무슨 일이

AI가 쓴 결과 문구가 "총지출이 더 큰 쪽"을 단가 판정에서 유추했다. A 2,000원·B 1,500원인데 "상품 B가 500원 더 커요".

예시 값(AC10)만 봤다면 지나쳤을 오류. 화면 테스트의 첫 사례가 다른 값을 넣어 잡았다.

어떻게 고쳤나

계산 로직에 spendMore(총지출이 큰 쪽)를 따로 두고, 로직 테스트 2건을 먼저 보강해 실패를 확인한 뒤 구현.

교훈: 단가와 총지출은 별개의 사실. 로직이 직접 답하게 하고, 테스트는 예시 값 말고 다른 값도 넣는다.

바이브 코딩에서 겪은 일 2

GPT 검토가 잡은 크래시, 그리고 직접 확인한 지적

묶음 개수에 아주 큰 수를 넣으면 화면이 깨짐

검증을 통과한 Infinity가 BigInt 변환에서 RangeError. 개수 9,999개·용량 1,000만 상한을 두고 총량을 BigInt로 계산.

0.0004g처럼 아주 작은 용량이 총량 0이 되던 문제도 같은 검토에서 → 소수 셋째 자리까지만 받도록

"표시 동률" 판정이 화면과 어긋난다

GPT: Math.round(1.005×100)은 100인데 화면은 "1.01". 바로 믿지 않고 Node로 직접 실행해 확인한 뒤, 화면과 같은 포맷 함수로 판정하도록 수정.

반대로 "색 토큰이 8개"라는 지적은 색상(hue)은 4개라고 근거를 들어 반영하지 않았다.

방법론의 장단점

빠르지만, 검증 없이는 믿을 수 없다

좋았던 점

  • 화면 초안과 설정(배포 워크플로, 테스트 환경)이 몇 분 안에 나온다
  • 테스트를 먼저 쓰게 하면 AI가 만든 코드의 오류를 그 자리에서 잡는다
  • 두 AI가 역할을 나누니 한쪽의 실수를 다른 쪽이 짚는다 (검토 지적 33건)
  • 기록이 남는다: 요청·결과·수정 이유가 DEVLOG에 그대로

조심할 점

  • 규칙 해석 실수: 총지출 방향, 큰 값 처리 — 사람이 숫자로 확인해야 한다
  • 요청하지 않은 것도 만든다: 범위를 문서로 못 박아야 했다
  • 도구 문제에 시간이 든다: 가짜 타이머로 테스트가 멈춤, Codex 샌드박스 오류로 자료를 직접 붙여야 했음
  • 검토 의견도 틀릴 수 있다: 직접 실행해 보고 반영 여부를 정했다
