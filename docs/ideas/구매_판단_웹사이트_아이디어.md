# 살까말까 웹사이트 아이디어

살까 말까 고민하는 순간과 구매 조건을 비교하는 순간을 돕는 소규모 웹사이트 아이디어다. 사용자가 관심을 보인 구매 숙려 리스트, 장바구니 할인 비교, 묶음상품 가성비 비교를 중심으로 정리했다.

프로젝트 이름은 **살까말까**로 확정했다. “지금 필요한 소비인지 생각하고, 구매한다면 조건을 비교한다”를 서비스 방향으로 잡는다. 아래 기능과 구현 범위는 주제 선택을 위한 제안이며, 최종 PRD 확정 전 단계다.

## 해결하려는 문제

- 할인이나 한정 판매 문구를 보고 급하게 구매한 뒤 후회한다.

- 할인율이 커도 최대 할인액이나 배송비 때문에 실제로는 더 비쌀 수 있다.

- 묶음상품과 대용량 상품의 개수·용량이 달라 가격을 바로 비교하기 어렵다.

- 무료배송이나 추가 할인을 받으려고 원래 필요하지 않던 물건을 더 담는다.

주요 사용자는 온라인 쇼핑 중 잠깐 계산이 필요하거나, 사고 싶은 물건을 며칠 두고 판단하고 싶은 사람이다. 첫 버전은 직접 입력하는 방식으로 만들고, 회원가입 없이 사용할 수 있도록 한다.

## 핵심 아이디어 세 가지

| 아이디어 | 사용자 질문 | 최소 기능 | 특징 |
| --- | --- | --- | --- |
| 구매 숙려 리스트 | 지금 꼭 사야 할까 | 상품명·가격·구매 이유 등록, 숙려 기간, 구매·포기 기록 | 구매 욕구의 변화를 기록 |
| 장바구니 할인 비교 | 어떤 쿠폰이 실제로 유리할까 | 정률·정액 할인, 최소 주문액, 최대 할인액, 배송비 비교 | 최종 결제액과 차액 표시 |
| 묶음상품 가성비 비교 | 어느 상품이 같은 양에 더 저렴할까 | 가격·개당 용량·개수·단위 입력 | 100g·100mL·1개당 비용 비교 |

### 구매 숙려 리스트

사고 싶은 물건을 등록할 때 필요한 이유와 예상 용도를 적는다. 1일·3일·7일 등의 숙려 기간이 지난 후에도 필요한지 확인하고, 구매·포기·추가 보류 중 하나를 선택한다. 숙려 기간은 구매를 막는 장치가 아니라 다시 생각할 기준으로 사용한다.

예시 흐름은 “헤드폰 129,000원 등록 → 기존 제품을 바꾸려는 이유 작성 → 3일 뒤 재검토 → 아직 필요하지 않아 포기”다. 첫 버전은 사이트를 다시 열었을 때 재검토 대상을 보여주고, 자동 알림은 추후 기능으로 둔다.

포기한 상품 가격의 합계는 **구매 포기 금액**으로 표시한다. 실제로 그 돈을 저축했다는 의미의 절약액으로 단정하지 않는다.

### 장바구니 할인 비교

비교할 조건을 각각 입력하면 할인 적용 가능 여부, 할인액, 배송비, 최종 결제액을 표시한다. 최소 주문액 미달은 할인 0원만 보여주는 대신 적용 불가 이유를 함께 안내한다.

계산 예시에서 상품 금액은 80,000원이다. A는 15% 할인에 최대 할인액 10,000원, 배송비 3,000원이므로 결제액은 73,000원이다. B는 8,000원 정액 할인에 배송비가 없으므로 72,000원이다. 두 쿠폰의 최소 주문 조건이 충족된다는 가정에서 B가 1,000원 저렴하다.

첫 버전은 비교안별 쿠폰 1개와 사용자가 입력한 최종 배송비를 다룬다. 복수 쿠폰 중복, 카드 할인, 포인트 적립, 쇼핑몰별 자동 정책 해석은 이후 범위다.

### 묶음상품 가성비 비교

같은 종류의 상품을 기준 단위로 환산해 비교한다. 총용량은 개당 용량에 개수를 곱해 구하고, 기준 단위당 가격과 총지출을 함께 보여준다.

예를 들어 A는 900mL 2개에 6,000원으로 100mL당 약 333.33원이고, B는 1.5L 1개에 5,400원으로 100mL당 360원이다. A가 단위당 약 7.4% 저렴하지만 결제 금액은 600원 더 크다. 비율의 비교 기준은 B다.

g와 kg, mL와 L는 각각 환산한다. 무게·부피·개수처럼 서로 다른 종류의 단위는 직접 비교하지 않는다. 단위 가격이 품질이나 실제 필요량까지 판단해 주지는 않으므로 결과는 가격 기준임을 표시한다.

## 확장 아이디어

| 기능 후보 | 제공할 도움 | 우선순위 |
| --- | --- | --- |
| 무료배송 추가 구매 비교 | 현재 주문과 상품 추가 후 주문의 총지출 비교 | 높음 |
| 구매 이유 재확인 | 최초 구매 이유와 숙려 후 생각을 나란히 비교 | 높음 |
| 대용량 사용량 비교 | 예상 사용량을 고려해 남는 양과 실제 사용량당 비용 표시 | 중간 |
| 사용 횟수당 비용 | 가격을 예상 사용 횟수로 나눠 비교 | 중간 |
| 구매 후 만족도 | 예상 용도와 실제 사용 경험 기록 | 중간 |
| 구독 본전 비교 | 구독료와 개별 이용료를 기준으로 필요한 이용 횟수 표시 | 낮음 |
| 구매와 대여 비교 | 이용 횟수별 구매 비용과 대여 비용 비교 | 낮음 |
| 옵션 업그레이드 비교 | 추가 가격과 실제로 쓸 추가 기능 정리 | 낮음 |

무료배송 비교 예시: 상품 27,000원에 배송비 3,000원이면 총 30,000원이다. 8,000원짜리를 추가해 무료배송을 받으면 총 35,000원이다. 결과는 “배송비 3,000원 감소, 총지출 5,000원 증가”로 보여주고, 추가 상품의 필요성은 사용자가 판단한다.

## 구현 방향 비교와 추천

| 방향 | 구성 | 장점 | 고려할 점 |
| --- | --- | --- | --- |
| 숙려 중심 | 숙려 리스트와 구매 이유 재확인 | 사용 경험과 제작 동기를 이야기하기 좋음 | 실제 사용 효과를 보려면 시간이 필요함 |
| 비교 중심 | 할인 비교와 묶음상품 비교 | 접속 즉시 쓸 수 있고 발표 시연이 명확함 | 계산 규칙과 예외 처리를 꼼꼼히 확인해야 함 |
| 통합형 | 숙려와 가격 비교 연결 | 필요성 판단부터 구매 조건 비교까지 연결 | 화면과 데이터 관리 범위가 커짐 |

**첫 구현은 비교 중심을 권장한다.** 사용자가 원한 “가끔 필요할 때 쓰는 간단한 웹사이트”에 가깝고, 입력부터 결과까지 짧게 시연할 수 있다. 할인 비교와 묶음상품 비교를 핵심으로 만들고, 무료배송 비교를 작은 추가 기능으로 둔다.

숙려 리스트는 독립적인 다음 단계로 남긴다. 기록형 앱에 더 끌린다면 숙려 리스트와 구매 이유 재확인만으로 시작해도 충분하다. 모든 후보를 한 번에 구현할 필요는 없다.

## 최소 구현 범위 제안

비교 중심 버전은 첫 화면에서 “할인 비교”와 “묶음상품 비교”를 선택한다. 각 도구는 두 개의 비교안을 입력받고, 결과 카드에서 최종 금액·단위 가격·차이를 보여준다. 예시 넣기와 초기화 버튼을 제공해 첫 사용과 발표 시연을 쉽게 한다.

- 필수: 두 비교안 입력, 계산 결과, 계산 근거, 입력 오류 안내, 모바일 화면.

- 추가: 무료배송 비교, 마지막 입력 기억하기.

- 이후: 숙려 리스트, 구매 기록, 데이터 내보내기.

- 초기 범위 밖: 로그인, 쇼핑몰 연동, 가격 자동 수집, 결제, AI 구매 추천.

브라우저에서 계산할 수 있는 범위로 시작한다. 숙려 기록이나 입력값을 브라우저에 저장한다면 같은 기기·브라우저에서만 유지되며, 브라우저 데이터 삭제 시 사라질 수 있음을 안내한다.

완료 기준은 예시 계산이 맞고, 단위 변환과 할인 상한이 정확하며, 빈 값·음수·0인 수량·비교할 수 없는 단위가 잘못된 결과로 이어지지 않는 것이다. 동률은 동률로 표시하고, 반올림한 표시값 때문에 비교 순서가 뒤집히지 않도록 원래 계산값으로 비교한다.

## 과제 진행용 Todo와 push 계획

다음은 개발 시 사용할 계획이며 아직 수행한 작업은 아니다. 처음부터 GitHub 저장소를 Public으로 설정하고, 아래 작업 묶음이 완료될 때마다 commit과 push를 남긴다. 긴 작업은 더 작은 Todo로 나눠 중간 결과도 올린다.

- [ ] 1단계: 주제와 핵심 기능 확정, Public 저장소 생성, PRD·Todo 작성 후 push.

- [ ] 2단계: 도구 선택 화면과 입력 폼, 예시 데이터 구현 후 push.

- [ ] 3단계: 할인 비교와 계산 근거 표시, 직접 계산한 예시 검증 후 push.

- [ ] 4단계: 묶음상품 비교와 단위 환산, 단위·수량 예외 처리 후 push.

- [ ] 5단계: 모바일 화면과 오류 안내 개선, 선택한 추가 기능 구현 후 push.

- [ ] 6단계: README·실행 방법·화면 캡처·발표용 사례 정리 후 push.

각 단계에서 AI에 요청한 내용, 실제 결과, 발견한 오류, 수정한 이유를 짧게 기록한다. Public 저장소에는 API 키나 개인 구매 내역을 넣지 않고 시연용 가상 데이터를 사용한다.

## 발표에 연결할 내용

| 과제 요구사항 | 발표에 담을 내용 |
| --- | --- |
| 제작한 것 소개 | 할인율·묶음 구성 때문에 비교하기 어려운 상황과 실제 시연 |
| PRD와 Todo | 대상 사용자, 핵심 문제, 최소 범위, 단계별 작업 기록 |
| 방법론의 장단점 | AI로 화면과 계산 코드를 만든 과정, 직접 검증하고 수정한 사례 |
| 개선이 필요한 점 | 복합 할인, 사용량 반영, 숙려 기록 등 구현하지 않은 범위 |
| 결론 | 구현 결과와 검증한 범위, 사용 후 확인할 효과 |

바이브 코딩의 예상 장점은 화면 초안을 빠르게 만들고 문구·배치를 반복 수정하기 쉽다는 점이다. 예상 한계는 AI가 할인 조건, 단위 변환, 반올림 기준을 잘못 해석하거나 요청하지 않은 기능을 추가할 수 있다는 점이다. 발표에서는 이 예상만 나열하기보다 실제 개발 중 겪은 사례로 바꾼다.

검증 사례는 최대 할인액 초과, 최소 주문액 미달, 1.5L와 900mL 묶음 비교, 수량 0, 같은 가격, 무료배송 때문에 지출이 늘어나는 경우를 포함한다.

결론의 방향은 “필요한 소비인지 생각하고 구매 조건을 비교하도록 돕는 작은 웹 도구를 구현했다”로 잡는다. 실제 절약이나 충동구매 감소 효과는 사용 기록을 모은 뒤 판단한다.

## 다음에 정할 사항

1. 비교 중심과 숙려 중심 중 첫 버전의 방향.

2. 제작 기간에 맞춘 필수 기능 수.

3. 확정한 이름인 살까말까에 어울리는 화면 분위기.

4. PRD 확정 후 개발 시작.

현재 추천 조합은 **장바구니 할인 비교 + 묶음상품 가성비 비교**이며, 무료배송 비교와 구매 숙려 리스트를 후속 후보로 둔다.
