- 모델: `gemini-3.5-flash-lite`(`worker/src/gemini.ts`의 주소). temperature 0, JSON 스키마 응답, 출력 토큰 상한(가격표 사진 읽기 6144, 치수 읽기·말로 담기·다나와 고르기 4096)(서버 설정 그대로). 상한은 2026-10-31에 더했고, 그 전의 조정용 확인 실행(아래)은 상한 없이 돌렸다.
- 프롬프트 판(프롬프트와 응답 스키마의 SHA-256 앞 8자리): 가격표 사진 읽기 `2efa7e1f`, 말로 담기 `0b81e1d4`, 다나와 같은 상품 고르기 `935a581f`, 치수 읽기 `e2c918b8`(2026-10-31, 아래 '판 기록'. 처음 판 `929dac41`은 2026-10-30 23:39 계산, 서버를 부르지 않고 `worker/src/readSize.ts`에서 읽음).
- 서버: 로컬 `wrangler dev`(`http://localhost:8787`, `ALLOWED_ORIGINS=http://localhost:5173`), 커밋 `272e6a1`의 작업 트리. 평가 스크립트는 실행할 때 아직 커밋 전이었고(결과 파일 `meta.git.dirty`에 `?? eval/`), 커밋 `207be64`의 `eval/`과 같은 내용이다(그 뒤 고친 것은 다나와 응답을 실패로 세는 `asDanawaPicks`뿐이고 가격표 사진 경로는 바뀌지 않았다).
- 실행 규칙: 사례당 1번, 사례 사이 7초, 한 번에 스크립트 하나, 다시 보내지 않음, 한 요청 60초 대기(앱과 같음).

### 판 기록

tuning-prompts 6단계의 판 기록이다. 판은 프롬프트와 응답 스키마의 SHA-256 앞 8자리다.

| 판 | 날짜 | 모델·설정 | 바꾼 규칙(전 → 후) | 이유(원인 분류) | 조정용 결과 |
| --- | --- | --- | --- | --- | --- |
| 치수 읽기 `929dac41` → `e2c918b8` | 2026-10-31 | `gemini-3.5-flash-lite`, temperature 0, JSON 스키마, 출력 토큰 상한 4096 | 스키마: 표기의 `w`·`d`·`h`를 `NUMBER` nullable(선택 칸) → `STRING` nullable(필수 칸, `required`에 `w`·`d`·`h` 추가). 프롬프트: 규칙 한 줄 추가 "w, d, h는 적힌 숫자를 단위 없이 글자로 적는다(예: "32", "47.5"). 읽을 수 없으면 null이다."(다른 줄은 그대로). 서버 정규화: 앞뒤 공백을 지운 글자가 숫자와 소수점만일 때 숫자로 바꾸고 범위 규칙(0 초과 1,000,000 이하)은 그대로(쉼표·단위·전각 숫자는 null, JSON 숫자도 같은 범위 규칙으로 받음) | 모델 한계. (1) NUMBER 칸에서 숫자를 `"w": 22.0000…`처럼 끝없이 이어 쓰는 반복을 직접 봤다(상한 4096을 넣은 호출 6번 중 4번이 MAX_TOKENS, 상한 없는 스트리밍 1번은 90초에 27,993토큰으로도 끝나지 않음). (2) 글자 칸으로 바꾸고 선택 칸으로 두자 모델이 `w`만 적고 `d`·`h`를 빼고 끝낸 응답이 1번 있어 세 칸을 필수로 했다. GPT 49번 상의(총괄 판정 R26), 필수 칸은 판정 R27 | 조정용 치수 자료가 없어 조정용 실행은 없다. 직접 만든 합성 캡처(평가 자료 아님) 4장(표기 1·3·6·6개, 정수·소수·축마다 다른 단위·빠진 축)으로 확인했다: 새 합성 입력 6회에서 숫자 반복 미재현 및 추출 정상 확인. 평가 자료(`_개인기록/평가/`)는 쓰지 않았고 치수 읽기 평가용은 한 번도 돌리지 않아 평가는 깨끗하다. 정답 파일 `eval/cases/read-size.json`(해시 `4053fc1f…` 그대로)과 채점기는 바꾸지 않았다(평가 스크립트는 서버가 정규화한 숫자를 비교한다) |

치수 읽기 정답(`read-size.json`)은 위 세 파일보다 나중인 2026-10-30 23:40 KST에 잠갔다. 그때까지 `/api/read-size`를 한 번도 부르지 않았고(서버·Gemini 호출 0번) 치수 캡처에도 조정용이 없어, 정답과 나누기는 모델 결과를 본 적이 없는 상태에서 정했다. 해시는 `sha256sum eval/cases/*.json`으로 다시 계산해 확인한다(앞의 세 파일 값은 그대로였다).

치수 읽기 정답은 한 번 다시 잠갔다(2026-10-30 23:49 KST). 처음 잠근 값(`906afe53447b098ebf6fc599034286c3dade15346f9945e77686d31171c7b625`)은 짝짓기 키워드 `textKeywords`를 표기마다 숫자 두 개로 적은 판이다. 리뷰에서 그러면 두 숫자 중 하나만 잘못 읽어도 짝이 끊겨 칸 5개가 모두 '못 읽음'이 되고(예: 32를 38로 읽었는데 '정답 32 → AI 빈칸'으로 보임) '틀림'이 거의 잡히지 않는다는 지적이 있어, 표기마다 사진에 적힌 숫자 하나로 바꿨다(같은 사진의 다른 표기 숫자 안에 들어가지 않는 숫자: sz11 32·36, sz15 35·95 등). 바뀐 것은 `textKeywords` 9개뿐이고 표기·kind·가로·깊이·높이·단위는 그대로다. 그 사이에 `/api/read-size`를 한 번도 부르지 않았고(서버·Gemini 호출 0번, `_개인기록/평가/결과/`에 치수 결과 파일 없음) 모델 결과를 본 적이 없어서 이 평가용은 아직 깨끗하다. 처음 값은 기록으로만 남기고 쓰지 않는다.

치수 읽기 정답은 한 번 더 다시 잠갔다(2026-10-31 01:13 KST). 직전 값 `4053fc1f341ff9a53b2d972e4e8a3c2194f64eb55df6b8f767c0b6b52471c3eb`는 기록으로만 남기고 쓰지 않는다. 이유: sz13의 짝짓기 키워드 `45`가 같은 캡처의 모델명 'HR-45'에도 들어 있어(키워드는 AI가 옮긴 글에 부분 문자열로 맞는지 본다) AI가 모델명을 표기 후보로 옮기면 정답 표기의 짝으로 잘못 잡힐 수 있었다. 같은 표기의 다른 축 값으로 바꿨다: 키워드 `45` → `30`(세로 30cm. 캡처의 다른 글 'HR-45'·24,800원·0.9kg·배송 안내에 들어 있지 않음). 바뀐 것은 sz13의 `textKeywords` 하나뿐이고 표기·kind·가로·깊이·높이·단위는 그대로다. 나머지 일곱 캡처의 키워드는 같은 방식으로 점검했고 겹치는 것이 없었다(`eval/lib.test.ts`가 캡처마다 치수 말고 숫자가 든 글을 적어 두고 키워드가 거기에 들어가는지 본다). 이번 변경에서 **치수 읽기 평가 스크립트(`eval/readSize.eval.ts`)를 한 번도 실행하지 않았고**(`_개인기록/평가/결과/`에 치수 결과 파일 없음, 평가용 캡처는 서버에 보낸 적 없이 눈으로 읽기만 하고 바꾸지 않았다) 이번 변경에서 서버·Gemini도 부르지 않았다. 2026-10-31 15-8 확인에서 `/api/read-size`를 실제로 부른 것은 평가 자료가 아닌 직접 만든 합성 캡처 4장뿐이다(위 설정 기록). 그래서 평가용 캡처의 모델 결과를 본 적이 없는 상태에서 정한 값이고, 이 평가용은 아직 한 번도 실행 전이라 깨끗하다.

4. 실제 자료로 평가용을 모은다: 자유 이용 가격표 사진 6장 이상(흐림·반사·가격 없음·행사가·회원가·단가·묶음), 실제 목소리 문장, 조회한 날 저장한 다나와 사본 6개 이상. 정답을 적고 해시를 잠근 뒤 마지막 판에서 한 번 돌린다. 요약(`src/ai/evalSummary.json`)은 평가용 결과로만 만든다: `node eval/summarize.ts --out src/ai/evalSummary.json <평가용 결과 파일들>`(손으로 숫자를 고치지 않는다).
5. 치수 정답 확인(Claude가 적은 것): 특히 sz13('세로'가 있어 적힌 순서대로 가로·깊이·높이로 본 정답)과 sz14(제품/포장 표기가 없어 '표기 없음'으로 적은 것). 고치면 평가용을 돌리기 전에 `read-size.json` 해시를 다시 적는다.
6. 치수 읽기 실제 자료: 상품 페이지 캡처로 조정용 몇 장과 평가용 6장 이상을 모은다(제품·포장 함께, 축 이름 없음, '세로', mm, '접었을 때/펼쳤을 때', 단위 없음, 단위 섞임, 치수 표기 없음을 포함). 직접 찍은 캡처나 자유 이용 자료만, 로그인 이름·주소·주문번호가 보이지 않는 것만, 같은 상품 페이지에서 나온 캡처는 조정용·평가용 한쪽에만 둔다. 자료는 `_개인기록/평가/치수/{조정용,평가용}/`에 넣고 정답을 적고 해시를 잠근 뒤 `node eval/readSize.eval.ts --set 조정용 --server http://localhost:8787` → (프롬프트를 고칠 일이 있으면 조정용 결과로만) → `--set 평가용` 한 번. 다른 평가 스크립트와 동시에 돌리지 않는다. 지금 평가용 합성 8장은 실제 자료가 모이기 전까지 쓰지 않거나 "합성 자료 성적"으로만 따로 적는다.

## 한계

- 작은 표본이고 일반적인 정확도를 뜻하지 않는다.
- 조정용 사진 8장은 사전 시험에서 결과를 본 자료라 정확도 근거가 될 수 없다.
- 다나와 평가는 저장한 사본 기준이다(실제 조회를 하지 않음). 합성 사본은 실제 페이지보다 단순하다.
- 치수 읽기는 평가 도구와 합성 자료 8장만 있고 정확도 숫자는 없다. 합성 캡처는 같은 틀의 표라 실제 캡처보다 쉽다. 치수 짝짓기는 표기마다 숫자 하나로 하므로 그 숫자를 잘못 읽으면 '틀림'이 아니라 '못 읽음'과 '더 읽음'으로 세어진다(나머지 두 축의 오독은 '틀림').
- `axes`(labeled·order)는 PRD F43의 채점 칸 다섯 개(가로·깊이·높이·단위·제품/포장)에 없어 채점하지 않는다. 그래서 sz13('세로')은 AI가 `order`로 표시했는지가 아니라 숫자가 적힌 순서대로 가로·깊이·높이에 들어갔는지만 본다.
- 응답 시간은 이 PC의 로컬 서버에서 잰 값이라 배포 환경과 다를 수 있다.
- 출력 토큰 상한(2026-10-31) 때문에 아주 긴 정상 응답도 잘린다. 잘리면 닫히지 않은 JSON이라 서버가 502를 돌려주고 앱은 "지금은 읽지 못했어요. 직접 입력해 주세요."를 보인다. 가격표 사진은 상품이 아주 많이(대략 30개 넘게) 찍힌 사진, 치수 읽기는 30줄이 넘는 치수 표가 그럴 수 있다.
- 치수 읽기 판 `929dac41`(숫자 칸)에서는 모델이 숫자 칸을 끝없이 이어 쓰는 일이 잦았다(상한을 넣은 실제 호출 6번 중 4번). 상한은 기다리는 시간만 약 11초로 줄일 뿐 이 실패를 막지 못한다. 판 `e2c918b8`(글자 칸)은 새 합성 입력 6회에서 숫자 반복 미재현 및 추출 정상 확인. 표본이 작고 합성 캡처라 반복이 다시 생기지 않는다는 뜻도, 정확도를 뜻하지도 않는다.
