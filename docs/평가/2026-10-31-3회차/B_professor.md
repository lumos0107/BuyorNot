### 4-2. 스킬 글 자체가 틀렸던 일(browser_close)은 어떻게 보여 줘야 하나

**무슨 일이었나**
- 17-5에서 스킬에 "MCP `browser_close`는 탭만 닫아 컨텍스트의 route가 남는다"고 적었다(79b00a0). 근거는 도구 출력에 찍힌 `await page.close()`였다(eval-round2/progress.md:12 "MCP browser_close = page.close()").
- 개발 2회차 전체 리뷰가 설치된 `@playwright/mcp` 0.0.83 코드를 읽어, `browser_close`가 컨텍스트와 브라우저를 통째로 닫고 출력의 `await page.close()`는 예시 글일 뿐임을 찾았다(final-review.md:49~52). 총괄과 재검토가 같은 코드를 다시 확인했다(final-rereview.md 3절).
- 고친 방식: 스킬(지금 쓰는 지시문)은 고쳐 쓰고, DEVLOG 17-5(기록)는 덧붙였다(DEVLOG.md:1161). 지시문은 맞아야 하고 기록은 남아야 하므로 이 구분은 옳다.

**고친 사실로 시험을 다시 읽으면**

| 비교 | 규칙 없이(시나리오 2) | 규칙과 함께 |
| --- | --- | --- |
| 모의 응답을 건 곳 | 공유 컨텍스트 `context.route`(skill-test-baseline.md:8·23) | 새 컨텍스트 |
| 정리 | 확인이 끝난 뒤 따로 `browser_close`를 부르기로 계획함(:273). 고친 사실로는 **이것으로 route가 사라진다.** 다만 같은 브라우저를 쓰는 다른 에이전트의 탭도 닫히고, 이 마지막 단계를 빼먹으면 실제 사고와 같다 | 같은 코드의 `finally`에서 `unrouteAll`·`close` |
| 남은 모의 응답 점검 | 없음(자기 가로채기가 먹는지만 probe로 봄, :31) | 빈 요청 `{}` → 400 확인 |
| 실제 호출 세기 | "로그가 보이면" 확인(선택, :275) | 시작·끝 두 번 셈(필수) |

- 그러니까 규칙 없이 쪽의 "'브라우저를 닫으면 함께 사라진다'고 가정"은 틀린 가정이 아니었다. 스킬 README의 시험 표(.claude/skills/README.md:85)는 괄호로 사실을 고쳤지만 여전히 이 가정을 '규칙 없이'의 잘못처럼 나열한다. 규칙의 실제 효과는 '정리를 같은 코드의 finally에 묶기(사고는 마지막 단계를 빠뜨려 났다), 남은 모의 응답 사전 점검, 로그 세기를 필수로'의 세 가지다. 이것도 의미 있는 차이지만 표가 말하는 것보다 좁다.
- '함께' 쪽은 틀린 근거가 들어 있던 판으로 돌렸고, 그 에이전트가 틀린 문장을 계획에 그대로 옮겨 적었다(skill-test-green.md:198 "browser_close는 컨텍스트에 건 route를 지우지 못하므로"). 고친 판으로 다시 돌리지 않았다.

**발표·질의응답에서 보여 주는 방법(권고)**
1. 숨기지 말고 P1과 한 쌍으로 보여 준다. 두 번 모두 같은 종류의 잘못이다. P1은 화면에 나온 결과를 실제 AI 결과로 믿었고, 이번에는 도구 출력에 찍힌 코드를 실제 동작으로 믿었다. 두 번 모두 진짜 출처(서버 로그, 설치된 패키지 코드)를 보고 바로잡았고, 두 번째는 리뷰가 평가 전에 잡았다. '보이는 출력은 동작의 증거가 아니다'라는 한 문장이 이 과목에서 배운 것으로 설득력이 있다.
2. 행동 규칙과 근거를 나눠 말한다. 규칙이 시키는 행동(새 컨텍스트, finally에서 닫기)은 처음부터 옳았고 근거 한 줄이 틀렸다. 근거가 틀려서 시험의 '규칙 없이'를 실제보다 나쁘게 셌다.
3. 스킬 README 표에 한 줄을 더한다: "규칙 없이 쪽도 마지막에 browser_close를 계획했고, 고친 사실로는 그것으로 모의 응답이 사라진다. 차이는 정리를 finally에 묶는 것, 남은 모의 응답 점검, 로그 세기다. 함께 쪽은 틀린 근거가 있던 판으로 돌렸고 다시 돌리지 않았다(판정 R42)." 원하면 고친 판으로 '함께'를 한 번 더 돌린다(서브에이전트 1회, 실제 AI 호출 없음).
4. 일반 교훈을 스킬에 남긴다: 스킬에 적는 도구 동작은 버전과 출처를 붙인다(고친 문장은 이미 "`@playwright/mcp` 0.0.83(`--isolated`)"을 붙였다). 스킬 글은 에이전트가 그대로 복사하므로 코드처럼 검증해야 한다.

## 5) 잘된 점

1. **틀린 결론을 스스로 찾아 바로잡았다.** 너무 잘 맞는 재현(글자까지 같은 세 줄)을 의심했고, 직접 호출과 서버 로그로 확인했고, 지난 기록은 그대로 둔 채 날짜를 단 정정을 덧붙였다. 영향받은 판정, 내려놓은 후보, 비교에서 뺀 결과를 하나씩 적었다.
2. **사고를 스킬로 바꾸고 시험했다.** 규칙 없이·함께 비교를 먼저 했고, 첫 시나리오가 답을 흘린다는 것을 알아채고 다시 했다. 평가기준과 지시 규칙이 그 스킬을 가리켜 다음 일에 실제로 적용된다.
3. **리뷰가 스킬 자체의 잘못을 잡았다.** 설치된 패키지 코드를 읽어 확인했고, 규칙의 행동은 유지하고 근거만 고쳤다. 지시문은 고쳐 쓰고 기록은 덧붙인다는 구분도 맞다.
4. **평가 B의 결정을 범위대로 지켰다.** 반드시 다섯과 하면 좋음 둘만 했고, 프롬프트·스키마는 건드리지 않았다. 서버 실패 구분이 앱 문구와 평가 채점까지 한 번에 맞물렸다.
5. **리뷰가 찾은 새 결함도 명세부터 고쳤다.** R43은 PRD v0.40 → 코드 → 테스트 순이고, 재검토가 고친 줄을 지워 테스트가 정말 막는지 봤다.
