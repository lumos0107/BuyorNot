## 1. 이견마다 내가 양보한 것과 고집하는 것

### 1-1. 순서: 사실 오류 먼저 vs 사용자 화면 먼저

| | 입장 |
| --- | --- |
| 채점 | 가 → 발표 재편 → 제작자 판정 준비 → 실측 → 스킬 마무리, 사용자 화면은 6번째에 "판정 줄 3 이하, PRD 먼저, 제작자 문구 승인" 조건으로 받음 |
| 비용 | 가 → 배포 전 게이트 문서 → 위험 포커스 → 평가 안전망 → 작은 화면·문구, 회고 ②a는 그 뒤 |
| R1의 나 | 합치기 → 회고 ②a → 삭제 포커스 → 캘린더 → 작은 손질, 사실 오류는 "별개로 지금" |

**양보한 것**
1. 사실 오류 묶음(가)이 어떤 코드 변경보다 앞선다. 문서만이고 반나절이며, 가7이 PRD 버전을 올리므로 사용자 화면용 PRD 수정이 그 위에 얹혀야 버전 줄이 꼬이지 않는다.
2. 제작자 판정 준비(꼭 볼 줄에 #28·#29 더하기)와 발표 초안은 Claude가 같은 세션에서 하는 일로 인정한다. R1에서 사용자 가치 0~1로 낮게 본 만큼 목록에서 내 몫이 작았을 뿐, 채점의 가장 큰 구멍(학생 판단 +3, 발표)을 Claude가 줄일 수 있는 유일한 방법이다(채점 1장).
3. 이번 묶음의 '제작자 확인 전' 새 줄은 3줄 이하로 묶는다(채점 하지 않을 것 3, 비용 4번 5의 "3줄 이하"). 23 → 30 → 34로 늘어난 수가 B의 문제 #1이다. 아래 목록은 새 줄 3(위험 포커스, 회고 ②a, 캘린더 문장)과 기존 줄 넓히기 둘(#25, #28)로 맞췄다.
4. 사용자 화면 쪽 PRD 문장은 먼저 쓰고 판정표에 올린 뒤 만든다. 코드부터 만들지 않는다.

**고집하는 것**
1. 사용자 화면은 "실측 뒤"가 아니다. 실측은 제작자가 사진 6~10장과 정답 확인을 해야 시작하므로(채점 6장 #5) 그동안 Claude의 일이 비게 된다. 회고 ②a·위험 포커스·캘린더 문장은 `worker/`·`eval/`·프롬프트·스키마를 건드리지 않아 안전망·스킬 문서 작업과 파일이 겹치지 않는다. 순서는 커밋 순서이지 배제가 아니다.
2. 이 목록에서 사용자에게 닿는 일은 이것뿐이다. 서버 없이 합쳐도 AI 탭·버튼은 숨고 나머지가 동작하며(README.md:254) 캘린더 줄·놓을 자리 확인은 늘 보인다(README.md:74). main에 push하면 GitHub Actions가 자동 배포하므로(README.md:236) 합친 뒤의 개선은 push마다 닿는다. 세션이 짧아 자르게 되면 아래에서부터 자르고(자름선 1-6) 사용자 화면은 마지막까지 지킨다.

### 1-2. 위험 확인 버튼 `autoFocus` 7곳은 제작자 결정이 먼저인가

사실 정리: 줄은 7개이나 고칠 곳은 5곳이다. `DeleteConfirm`(`WishlistScreen.tsx:1266`) 하나가 고민 중(:779)·결정 기록(`HistoryScreen.tsx:259`)·구독(`SubscriptionScreen.tsx:438`)을 모두 덮고, 나머지는 `ExampleBar.tsx:24`, `ResetConfirm.tsx:32`, `BackupSection.tsx:113`, `HistoryScreen.tsx:273`('옮기기', 평가자 D의 6곳 밖)이다. 규칙은 `PRD.md:337`(2026-10-11 GPT 검토로 정한 2차 공통 규칙 "확인 단계는 들어가면 확인 버튼에")과 `:439·:446·:466`에 글로 있다. 삭제에는 되돌리기가 없다(`useWishlist.ts:175`).

**양보한 것**
1. 이것은 새 기능이 아니라 **이미 받아들여진 규칙을 뒤집는 일**이다. 새 줄을 '확인 전'으로 표시하고 먼저 만드는 R38의 방식(판정표.md:8)과는 결이 다르다는 비용 관점의 지적을 받아들인다. 그래서 반드시 판정표 새 줄(#35)로 올리고 '꼭 볼 줄'(판정표.md:11이 "문구가 아니라 동작을 정한 줄"을 먼저 보라고 한 기준)에 넣는다.
2. 7곳 전부를 한 번에 같은 규칙으로 바꾼다. 처음에는 되돌릴 수 없는 곳(삭제 셋, '바꾸기')만 바꾸자고 할 생각이었으나, '옮기기'는 메모·회고를 지우고(PRD.md:446 "결정 메모와 회고는 지워져요") 예시·초기화도 "일부만 예외"로 가르면 `PRD.md:337`에 조건 문장이 필요하다. 가르는 기준을 내가 만들어 내야 해서 "확인 단계는 들어가면 [취소]에" 하나로 쓰는 편이 규칙이 단순하다. 고칠 곳 5곳, 시험 4줄(위 확인 목록), PRD 4줄(337·439·446·466)과 머리 주석 둘(ExampleBar.tsx:5, ResetConfirm.tsx:4)이다.
3. [취소]로 옮기면 "‘…’을 지울까요?" 문장이 낭독에서 빠지므로 확인 그룹에 `aria-describedby`로 그 문장을 잇는다(비용 3.4, F32·F44와 같은 방식). 공통 컴포넌트로 묶는 일(비용 다10)은 하지 않는다.

**고집하는 것**
1. 제작자 결정을 **기다리지 않는다.** 이유는 저장소에 있다. 이 일은 평가 1회차(P7)에서 보류, 평가 2회차에서 "다음 회차 1순위"로 미룸 두 번 연속 미뤄졌고(2회차.md 5장 '미룸'), 판정표 34줄은 세 회차째 0줄 판정이다(B 6장 #1). "제작자 결정 뒤"가 조건이면 세 번째 미룸이 된다. 판정표.md:5·7은 제작자가 '아니오·바꿈'이라 하면 PRD부터 고치고 코드와 테스트를 맞추는 되돌리기 절차를 이미 정해 두었다.
2. 그러니 방식은 이렇다. PRD를 먼저 'Claude 결정, 제작자 확인 전'으로 고치고, 같은 커밋 묶음으로 코드·시험을 맞추되 **자기 커밋 하나**로 한다. 판정표 이유 칸에 되돌리는 법 한 줄("`autoFocus` 5곳을 원래 버튼으로")을 적는다. 제작자에게는 '꼭 볼 줄' 맨 위에서 예/아니오 한 번만 묻는다.
3. 위험 비대칭이 근거다. 해서 틀려도 키보드 사용자가 Tab 한 번 더 누르는 불편이 전부인데(되돌리기 5줄), 안 해서 틀리면 Enter 한 번으로 기록 전체가 사라지거나(삭제) 지금 기록이 파일로 교체된다(바꾸기, `PRD.md:466`).
4. 이견으로 남는 것: 비용 관점은 "제작자 결정 뒤"를 표에 그대로 둔다(비용 4장 3번). 나는 위 방식(먼저 만들고 꼭 볼 줄 맨 위에서 확인)을 최종 기록에 적자고 한다. 제작자가 아니오라고 하면 되돌리는 값이 작다는 점이 내 근거다.

### 1-3. P8(묶음 라벨 거절)은 문구만

세 관점이 거의 합의했다(채점 하지 않을 것 2, 비용 3.3). 차이는 얼마나 앞에 두느냐이다.

**양보한 것**
1. 프롬프트·스키마는 고치지 않는다. 재개 조건은 비용 3.3의 여섯 단계를 그대로 최종 기록에 옮긴다: 조정용에 총액+단가 병기 라벨 사례를 제작자가 모음 → 원시 응답을 읽고 원인 분류를 기록 → 일반 규칙 하나 → 같은 조정용으로 전후 비교와 단가만 있는 사례(rt04)가 깨지지 않는지 → 판 기록 → 새 평가용으로 성적표. 비용의 비대칭 위험(모델이 `priceBasis`를 덜 붙이면 단가가 총액 칸 '채울 값'으로 확인 상자까지 가는 반대 실패, `bundleFill.ts:27~28`의 "단가로 총가격을 추정하지 않는다")을 받아들인다.
2. 내 R1의 나4(b) "맞게 읽은 용량·개수 살리기"는 다음 목록의 맨 아래 조건부로 내린다. 단가 라벨 응답의 `size`를 믿어도 되는지 자료가 한 건뿐이다(비용 나12. 평가 채점이 '100g당' 가격표에서 AI가 100을 용량으로 넣는 경우를 따로 세는 것, 판정표 #16, 도 같은 위험을 보여 준다).
3. 표현을 낮춘다. R1에서 "표준 마트 라벨"이라고 쓴 곳은 사실이 아니다. 합성 라벨 한 장으로 실제 호출 2번(평가 1회차, 평가 C) 중 2번 거절이고 정확도가 아니다(비용 3.3 표본의 한계).
4. 관측을 `docs/ai-eval.md`에 기록하는 일(비용 가9)은 (가)에 넣는다. `2026-10-31-2회차.md:216`의 '미해결'("평가 B는 스텁으로만 봤다")은 날짜 달린 기록이라 고치지 않고 `ai-eval.md` 한계 절에 덧붙인다.

**고집하는 것**
1. 문구(거절 문장에 읽은 숫자)는 "나중"이 아니라 다음 목록 안에 둔다. 서버를 켠 빌드에서 사용자가 보는 AI 실패는 이것 하나이고, 사진의 6,480원을 보면서 앱이 "100mL당 가격으로 읽었어요"라고만 하면 어느 쪽이 틀렸는지 알 수 없다(A H1). 프롬프트·스키마를 안 바꿔서 원칙 2에 닿지 않으며, 2회차 R38이 미룬 조건("실제 응답을 본 뒤", I8)이 이번에 채워졌다.
2. 판정표는 새 줄을 만들지 않고 #25(`판정표.md:39`, F32 단가 거절 문장)를 넓힌다.
3. 대신 사용자 화면 목록에서는 AI 없는 순환(회고·삭제·캘린더) 뒤에 둔다. 이 문장은 서버를 배포해야 보이므로(README.md:254) 채점의 "낮음"과 같은 칸에 있다는 점은 받아들인다. 문장 모양은 "AI가 ‘6,480원’을 100mL당 가격으로 읽었어요. …"처럼 읽은 값을 따옴표 안에 두어 F32 성공 줄(`bundleFill.ts:69`)과 맞춘다. 읽은 가격은 `tagToBundle`의 `item.price`(`bundleFill.ts:62`)에서 이미 쓸 수 있다.

### 1-4. 무료 한도 관련 항목

**양보한 것**
1. 한도 숫자 읽기는 배포와 같은 날이 아니라 **배포를 정하기 전에** 제작자가 한다. 비용 3.1의 계산(배포 날 Step 4·5와 합성 평가용 한 번만으로 Gemini 요청이 30 안팎)이 숫자 없이는 평가용 한 번이 모자랄지도 말할 수 없다는 것을 보여 준다. 평가용은 한도를 확인한 날, 시연 준비와 다른 날 돌린다(비용 판단).
2. 하루 총량 상한·시연 코드·`GET /api/status`는 배포를 정한 뒤로 미룬다. 내 R1이 이미 그랬고 비용도 같다. `wrangler.jsonc`에 `observability` 등 검증 못 한 키를 미리 넣지 않는다(비용 3.1 #2). 배포 날 확인 단계로만 적는다.
3. 테스트 2개(꺼짐+키 없음 → 503, 제한 초과+키 없음 → 429)와 요약의 '뺀 요청' 비율 경고는 S이고 순서를 못 박으므로 목록에 넣는다. R1에서는 목록 밖이었으나 평가용을 한 번만 돌릴 수 있다는 점(사례당 한 번)이 이유다.

**고집하는 것**
1. 이 묶음은 사용자 가치가 배포 전에 0이다(README.md:6, 비용 3.1 "지금 노출은 0이다"). 그래서 Claude의 한 세션이 모자랄 때 회고·위험 포커스보다 앞에 두지 않는다. 비용의 4장은 게이트 문서를 2번에 두었으나 같은 세션에서 문서로 끝낼 수 있는 S라 앞뒤가 큰 문제가 아니다. 자름선은 1-6에 둔다.
2. 제작자 몫은 하나다: AI Studio에서 분당·하루·읽은 날짜를 읽는 것. 이 숫자는 Claude가 쓰지 않는다(비용 나3). 이것을 합치기와 서버 배포 결정의 전제로 최종 기록에 적는다.

### 1-5. 회고 ②a의 자리

**양보한 것**
1. 두 걸음으로 나눈다. 걸음 1은 문구와 날짜만(고민 목록에 "돌아볼 물건 n개", 결정 기록 구매함 카드에 "11/7부터 적을 수 있어요"). 걸음 2는 "보러 가기" 버튼, 탭 전환, 첫 회고 카드 포커스다. 걸음 2는 숨은 패널이 포커스를 못 받아 전환 뒤에 그려야 해서 M이 될 수 있다는 비용의 위험(비용 다1)을 받아들이며, 걸음 2가 길어지면 걸음 1만 내고 그친다.
2. 각 걸음을 자기 커밋·자기 시험으로 하고(비용 4장 끝) PRD를 먼저 쓴다. 새 판정 줄은 걸음 1·2를 합쳐 한 줄(#36)이다.
3. 구매함 직후 한 줄(#32)은 이미 '꼭 볼 줄'에 있다(판정표.md:11). 제작자 판정을 먼저 받으면 좋다는 비용의 말에 동의한다. 판정이 아니오·바꿈이면 걸음 1의 문구를 맞춘다.

**고집하는 것**
1. #32의 판정을 **기다리지 않는다.** 걸음 1은 `RETRO_AFTER_MS`(`summary.ts:9`)에서 날짜를 만들 뿐이라 #32의 문장과 논리적으로 독립이고, 판정표는 세 회차째 판정이 없다. 걸음 1을 비용의 "5개 뒤"가 아니라 사실 오류 묶음 바로 다음(사용자 화면 중 첫째)에 둔다. 이유는 세 가지다. 순환의 가장 큰 새는 곳이라고 A·E가 따로 꼽았고(A 7장 2, E 7장), `reviewDue`를 쓰는 곳이 결정 기록 카드 한 곳이며(`HistoryScreen.tsx:189`), 회고가 비면 사기 전 점검의 "비슷한 구매 회고"(`similar.ts:59`)와 요약의 후회 건수(`summary.ts:39`)도 비어 간다.
