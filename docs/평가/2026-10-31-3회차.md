# 다각도 평가 3회차(평가 C)와 최종 기록 (2026-10-31)

- 대상: 브랜치 `ai-stage1` 커밋 `0b89f64`(개발 2회차 17-1~17-6과 전체 리뷰 뒤 최종 수정까지, PRD v0.42, 자동 테스트 1551개, 서버 미배포, 실제 자료 정확도 평가 전)
- 요청: 제작자 "평가 → 결정 → 개발 → 평가를 2번, 마지막엔 다각도로 평가하고 추가할 것·개선점까지 기록". 개발 1회차(16단계)와 개발 2회차(17단계)를 마쳤으므로 이번이 마지막 평가이고, 개발 3회차는 하지 않는다.
- 방법: 고정 기준 [평가기준.md](평가기준.md) 그대로. 평가 에이전트 5명(A 실제 사용자는 브라우저 360px, B 교수, C 보안·신뢰성, D 접근성·문구, E 기능 기획) → 세 관점(사용자 가치·채점 가치·비용 위험) 토론 2라운드 → GPT 상의(52번) → 결정(판정 R44). 이번 토론은 개발 범위가 아니라 이 최종 기록을 정했다. 다른 Claude 세션은 쓰지 않았다(평가자와 토론자는 모두 이 세션의 서브에이전트).
- 실제 AI 호출(서버 로그 기준): 평가자 A만, 모델 호출 3번(가격표 읽기 1번, 묶음 라벨 읽기 1번, 치수 읽기 1번). 로컬 AI 서버 로그의 `POST /api/` 줄이 평가 시작 전 8줄, 끝난 뒤 14줄이었다. 늘어난 6줄은 빈 요청 400 두 번, `/api/read-tag` 200 두 번, `/api/lowest-price` 200 한 번(다나와 조회가 꺼져 모델을 부르지 않음), `/api/read-size` 200 한 번이다.
- 남은 모의 응답 점검: 평가자 A가 시작 전에 브라우저를 닫고 새로 연 뒤 앱 페이지에서 빈 요청(`{}`)을 보내 400을 받았다(스킬 `testing-ai-screens` '브라우저로 확인할 때' 4항). 모의 응답은 F32 성공 상자를 보려고 한 번만, 새 컨텍스트에서 걸고 `finally`에서 풀고 닫았으며 결과에 "모의 응답"으로 적었다. 총괄이 평가 뒤 빈 요청 두 번으로 다시 400을 확인하고 브라우저를 닫았다.
- GPT 52번: 지시가 '2번'이므로 개발은 멈추고 (가) 사실 오류만 고친 뒤 최종 기록을 남기는 데 동의. 다음에 할 것의 순서에 동의하고, 위험 확인 첫 포커스는 질문 한 줄을 먼저 보내되 '취소'를 권하라고 함. 스킬 시험 정정은 날짜를 달고 확인된 차이를 셋으로 한정하며 재시험은 필수가 아니라고 함. 보고는 범위 → 한계 → 제작자 결정 순서.
- 원문: 같은 이름의 폴더 `2026-10-31-3회차/`(A~E 평가, R1·R2 토론). 로컬 절대 경로는 '(저장소 밖 임시 폴더)'·'(작업 루트)'·'(사용자 이름)'으로 바꿨다. 토론 파일마다 (가)의 번호가 다르며, 이 기록은 `R2_cost_risk.md` 2.1의 번호를 따른다.

2. **조정용 비교 자료 없이 프롬프트·스키마를 바꾸지 않는다(원칙 2).** P8도 여기에 든다. 지금 할 수 있는 것은 거절 문장에 읽은 숫자를 넣는 앱 문구와 정직한 기록(가9)까지다. 같은 입력의 출력 흔들림(`x`/`×`, 상품명), temperature, 긴 캡처 축소 규칙도 같다. 한 번 본 이상한 결과는 먼저 서버 로그의 `POST` 줄로 출처를 본다. 이유: 지금 P8의 실패는 맞는 값을 채우지 않는 안전한 쪽이고, 고쳐서 `priceBasis`를 덜 붙이면 단가가 총액 칸으로 가는 반대 실패가 생길 수 있다(`bundleFill.ts:27~28`).
3. **제작자 판정 전에 '제작자 확인 전' 줄을 크게 늘리지 않는다.** 판정표는 세 회차째 판정이 0줄이고 확인 전 결정은 23 → 30 → 34로 늘었다. 판정, README 학생 서술 칸, 평가 정답, 결론, temperature 0의 이유를 Claude가 대신 쓰지 않는다(대신 쓰면 학생 판단 점수가 오히려 깎인다, B 11장).
4. **검토를 거친 화면을 여는 구조 변경과 검증하지 못한 설정을 배포 전에 넣지 않는다**(세 관점 합의). 알림 칸 통일, 위험 작업 공통 확인 컴포넌트(N17), 화면 파일·스킬 스크립트 리팩터링, `wrangler.jsonc`에 `observability` 등을 미리 쓰기, 개발 의존성 취약점 1건(`undici`, 배포 번들에 없음)을 고치려고 테스트 환경을 바꾸는 일, 새 스크립트 추가.

## 7. 미해결

- 묶음 라벨(P8)의 거절 빈도: 같은 합성 라벨 한 장을 실제로 2번 읽혀 2번 거절했다. 실제 마트 라벨에서 얼마나 자주인지는 모른다. 다시 볼 조건(5-3의 2)이 차기 전에는 프롬프트를 고치지 않는다.
- 치수 읽기의 실제 정확도: 이 합성 캡처의 실제 기록은 4번 모두 정답이지만 한 장이라 정확도가 아니다. 실제 캡처 평가용은 아직 없다.
- 같은 입력에서 출력이 흔들림: 관찰이 한 건씩 늘었을 뿐 원인과 빈도는 모른다.
- 스킬 규칙의 효과: 비교 시험은 두 쪽 조건이 달라 효과를 따로 입증하지 못했다. 평가 C가 규칙을 따른 첫 실제 사례이고, 같은 조건의 재시험은 하지 않았다.
- 확인 상자 설명 연결의 실제 낭독: 자동 테스트와 DOM은 연결만 본다. 폰 스크린리더로 확인하기 전까지 모른다.
- 긴 스크롤 캡처: 계산만 있고 모델 반응은 모른다.
- 가격표 읽기 숫자 칸의 같은 숫자 반복 위험: 관측 없음, `docs/ai-eval.md` 한계 그대로.
- 무료 한도 숫자: 빈칸이라 공개 배포 때 하루 상한이 필요한지 판단할 근거가 없다.
- 실제 자료 정확도: 숫자 0개, 성적표 요약은 처음 값 그대로.
