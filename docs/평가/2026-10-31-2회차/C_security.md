## 5) P1 읽기 크기 없는 숫자: 신뢰성 평가와 (가)~(라) 권고

### 5-1. 실제 사용자에게 어떤 위험인가
- 형태: 에러가 아니라 정상 응답이다. 서버 검사(모양·범위)와 앱 검사(`isReadSizeResponse`)를 모두 통과한다. 그래서 감시·재시도·429 같은 장치가 모두 무관하고, 남는 방어는 사람의 대조 하나뿐이다.
- 사람의 대조가 약한 이유: 지어낸 값이 프롬프트 말을 써서 형식이 정상이다. 크게 보기는 접혀 있고, 긴 캡처에서 해당 줄을 찾기가 번거롭다. 후보가 하나뿐이면 자동 선택된다.
- 피해: 놓을 자리 판정이 틀려 사기 전 점검으로까지 번진다. 이 앱의 목적(충동구매를 줄이는 근거를 주는 것)을 거꾸로 건드리는 종류의 오류라 중간 이상으로 본다.
- 빈도: 모른다. 같은 사진에서 3번 중 1번 틀렸다는 관찰이 전부이고, 1회차 기록도 말하듯 표본이 너무 작다. 0/20이 나와도 95% 상한이 약 15%(3/20)라 "드물다"의 근거가 못 된다.
- 단서: 지어낸 말이 프롬프트의 예시 낱말·구분자와 같다. 모델이 사진을 근거로 삼지 못한 순간 프롬프트 예시를 내용처럼 채웠다고 보는 것이 현재 가장 단순한 설명이다. 확정은 아니다.

## 7) 추가 기능 제안 (PRD F36~F42와 겹치지 않음)

1. `GET /api/status`와 앱의 "AI 쉬는 중" 표시(S): 켜짐·꺼짐·다나와 상태만 알리고 Gemini는 부르지 않는다. 배포 날 스모크 시험과 시연 직전 점검이 한 번에 된다. 이때 꺼진 다나와는 앱이 서버에 상품명을 보내지 않고 검색 주소를 직접 만들 수도 있다(C6 (d)).
2. 하루 총량 상한과 `daily_limit` 응답(M): Durable Object(무료 SQLite) 등으로 하루 호출 수를 세어 한도 앞에서 멈춘다. 무료 요금제에서 되는지 확인 필요. 이 점 때문에 (라)처럼 호출을 늘리는 설계는 이 상한이 있을 때 안전해진다.
3. 시연 코드(S~M): `ACCESS_CODE` 비밀 변수와 앱 설정 칸. 한도 소진·남용이 한 번이라도 보이면 켜는 비상 카드.
4. "이 앱이 보내는 것" 안내 한 화면과 README 표(S): 기능별로 무엇이 어디로 가는지, 저장 여부.
5. 스모크 시험 스크립트(S): 잘못된 본문 400·429, 다른 Origin 403, 키 누락 503을 한 번에 돌린다. 실제 Gemini는 경로마다 한 번만.
