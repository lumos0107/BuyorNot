# 다각도 평가 기준 (고정, 2026-10-31)

평가를 여러 번 하면서 결과를 비교하려고 조건과 항목을 고정한다(GPT 50번). 평가 A(1회차, 2026-10-31), 평가 B(개발 1회차 뒤), 평가 C(개발 2회차 뒤)가 이 문서를 같이 쓴다. 기준을 바꾸면 이 문서 아래 '바꾼 기록'에 날짜와 이유를 남기고, 바꾼 항목은 이전 결과와 직접 비교하지 않는다.

## 1. 조건

| 항목 | 값 |
| --- | --- |
| 화면 | 360×800(휴대폰), 필요하면 1280×800 한 번 |
| 앱 | 로컬 개발 서버 `http://localhost:5173/BuyorNot/`(`VITE_AI_SERVER_URL=http://localhost:8787`) |
| AI 서버 | 로컬 `wrangler dev`(:8787), 다나와 자동 조회 꺼짐(`DANAWA_ENABLED=false`) |
| 모델·설정 | `gemini-3.5-flash-lite`, temperature 0, 출력 상한 가격표 6144·나머지 4096, 프롬프트 판은 `docs/ai-eval.md` 판 기록 |
| 실제 AI 호출 | 평가 한 번에 최대 3번(사진 읽기 1번 = 1호출) |
| 입력 자료 | `docs/평가/기준자료/`의 합성 HTML을 그 자리에서 그림으로 만들어 쓴다(가격표 `src_pricetag.html`, 묶음 라벨 `src_bundle.html`, 상세 캡처 `src_capture.html`). `_개인기록/평가/`(평가용 자료)는 쓰지 않는다 |
| 기록 | 평가한 커밋 해시, 날짜, 실제 호출 수, 스크린샷 위치 |

## 2. 평가자와 고정 항목

평가자마다 아래 고정 항목은 반드시 같은 방식으로 1~5점과 근거를 적고, 그 뒤에 자유 탐색으로 찾은 것을 따로 적는다.

### A 실제 사용자(충동구매를 고민하는 대학생, 처음 켬, 브라우저)

| 번호 | 과제 | 보는 것 |
| --- | --- | --- |
| A1 | 첫 화면을 30초 보고 앱이 무엇을 하는지 말해 보기 | 목적이 보이나 |
| A2 | 사고 싶은 물건 하나를 손으로 담고, 담긴 것을 찾기 | 담은 뒤 확인이 보이나 |
| A3 | 가격 비교 → 가격표 사진(`src_pricetag.html`) → 읽은 상품 → 온라인 가격 확인 → 고민 목록에 담기 | 흐름이 끊기지 않나, 담기 폼 값이 맞나 |
| A4 | 묶음 비교 카드 A에 사진으로 채우기(`src_bundle.html`) | 채운 값과 안내 |
| A5 | 고민 중 카드의 놓을 자리 확인에 치수를 적고 저장, 캡처에서 치수 읽기(`src_capture.html`) | 결과 문장, 읽은 값이 사진과 같은가 |
| A6 | 캘린더 버튼, 결정·회고, 사기 전에 한 번 더 | 끝까지 이어지나 |

### B 교수(인공지능 프로그래밍 중간 과제 채점)

| 번호 | 항목 |
| --- | --- |
| B1 | 제품 안의 AI 활용이 의미 있나 |
| B2 | 스킬로 과제를 수행했나(스킬이 실제로 쓰이고 지켜졌나) |
| B3 | PRD → 계획 → 테스트 → 리뷰의 근거 있는 개발 |
| B4 | AI 평가의 정직성과 엄밀성 |
| B5 | 학생 자신의 판단이 보이나 |
| B6 | 문서와 발표 준비(README = 5분 발표 구조) |
| B7 | 예상 질문 5개 이상과 좋은 답에 필요한 것 |

### C 보안·개인정보·신뢰성

C1 키 보관, C2 남용·비용(무료 한도), C3 기기 밖으로 나가는 데이터와 안내, C4 배포판 CSP, C5 사용자가 실제로 만날 실패(Gemini 429·503·시간 초과·숫자 반복), C6 다나와 약관과 기본 꺼짐, C7 배포 날 확인 목록.

### D 접근성·문구(코드로)

D1 포커스(채운 뒤·취소 뒤·실패 뒤), D2 알림 칸(role=status/alert가 글보다 먼저 있나), D3 비활성 버튼의 이유, D4 같은 이름 버튼, D5 대비, D6 터치 영역, D7 문구(쉬운 말, 기능끼리 일관, `check_copy.py`).

### E 기능 기획

E1 핵심 순환(담기 → 고민 → 결정 → 회고)의 새는 곳, E2 추가 기능 후보(문제·방법·AI 적합성·개인정보/비용·품·검증), E3 다음에 할 것 3개와 하지 않을 것 2개.

## 3. 결과 형식(모든 평가자)

1) 한 줄 총평 2) 고정 항목 점수와 근거 3) 잘된 점 4) 문제(심각도, 근거: 파일:줄 또는 화면·재현 순서) 5) 개선 제안(품 S/M/L) 6) 추가 기능 제안(PRD 후보 F36~F42와 겹치면 번호) 7) 가장 먼저 할 일 3개. 이전 회차가 있으면 '지난 회차 문제가 고쳐졌나'를 표로.

## 4. 결정 방법

평가자 결과 → 세 관점(사용자 가치·채점 가치·비용 위험) 2라운드 토론 → GPT 상의 → 결정(판정 번호) → 기록(`docs/평가/YYYY-MM-DD-N회차.md`).

## 5. Claude가 하지 않는 것(제작자 몫)

평가 정답 쓰기·확인, PRD '제작자 확인 전' 판정, README의 학생 목소리 부분(4~6장 서술, '스킬로 과제를 한 방법'의 소감), 마감일 확인, 서버 배포·push, 다나와 자동 조회를 켤지.
