# 개발 기록(DEVLOG)·README 갱신

## 개요

DEVLOG.md는 과제 산출물이다. 작업 하나마다 같은 표 양식으로 "AI에게 무엇을 시켰고, 무엇이 나왔고, 무엇을 고쳤고, 어떻게 확인했는지"를 남긴다. README.md는 5분 발표 구조라 되도록 그대로 두고 정해진 곳만 고친다.

## DEVLOG 항목

파일 끝에 붙인다. 제목은 `## YYYY-MM-DD · 기능 번호 · 한 줄 요약`.

| 항목 | 기록 내용 |
| --- | --- |
| 날짜와 작업 번호 | 날짜, TODO 번호(예: 14-3), 계획 작업(계획 ai-stage1 T3), 관련 GPT 상의 번호 |
| 연결된 기능과 검증 ID | `F44 / AC64·AC65 (PRD v0.24)` |
| AI에 요청한 내용 | 제작자 요청 원문이나 계획 작업, Claude가 에이전트·GPT에게 맡긴 것 |
| 생성 결과와 발견한 문제 | 만든 것, 테스트·리뷰·GPT가 잡은 문제(구체적으로: 무엇을 넣으면 무엇이 나왔나) |
| 수정한 내용과 이유 | 무엇을 왜 고쳤나, 출처(GPT NN번, 제작자 결정) |
| 검증 결과 | 구현 전 실패 확인, `npm test` 통과 수/전체, oxlint, tsc, 그 밖에 직접 확인한 것 |
| commit 식별자와 push 확인 | 코드 커밋의 해시(이 기록은 그 뒤 기록 커밋에 넣는다), push 안 함 |
| 남은 작업 | 다음 작업 번호, 제작자 결정 대기 |

- 사실만 쓴다. 숫자(테스트 수 등)는 이번에 실제로 돌린 출력에서, 언제 돌린 것인지와 함께 옮기고, 확인하지 않은 것은 "확인 안 함"이라고 쓴다.
- 지난 항목의 표현은 고치지 않는다. 사실이 틀렸으면 그 항목 끝에 `(YYYY-MM-DD 정정: …)`을 덧붙인다.

## README에서 고치는 곳

- 맨 위 상태 줄과 테스트 개수(`npm test` 실제 값), 3장 "개발 진행" 표의 단계 행, 기능이 화면에 생겼으면 1-4 기능 목록·2장 화면 설명, 7장 실행 명령이 바뀌었으면 그 명령.
- 4~6장(장단점·개선점·결론)은 발표 원고라 제작자가 요청할 때만 고친다. 그 안의 숫자나 사실이 TODO·PRD와 어긋나면 "README 4장 '자동 테스트 532개'가 지금 571개와 다름"처럼 구체적으로 보고하고 제작자 판단을 받는다.

## 자주 하는 실수

- 테스트 개수를 짐작해 쓴다 → 방금 돌린 `npm test` 출력에서.
- 여러 작업을 한 항목에 뭉친다 → 작업마다 한 항목(같은 날 여러 개 가능).
- README의 발표 문단까지 새 기능 설명으로 바꾼다 → 정해진 곳만.
