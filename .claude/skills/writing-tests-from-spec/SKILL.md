# 명세를 테스트로

## 개요

테스트의 기대값은 코드가 아니라 PRD에서 온다. 검증 사례(AC) 표의 입력과 기대 결과를 한 줄씩 옮기고, 구현 전에 실패하는 것을 본다(superpowers:test-driven-development).

## 절차

1. **찾기**: PRD 11장의 해당 AC 행과 기능 절(`### Fnn`), 계획 작업의 Interfaces·테스트 이름 목록을 읽는다. AC 행은 입력과 기대 결과가 ` / `로 같은 순서로 나뉘어 있다.
2. **옮기기**: 입력 하나 = 기대 결과 하나 = 단언 묶음 하나. 한 `it`에 여러 사례를 넣을 때도 사례마다 단언을 따로 둔다.
   - **화면 문장**은 PRD 따옴표 안을 글자 그대로 복사한다(가운뎃점 `·`, 화살표 `→`, 괄호, 마침표까지). 기억으로 다시 쓰지 않는다.
   - **숫자**는 PRD 값을 쓰고, PRD에 없는 중간값(예: mm 여유)은 PRD 규칙으로 계산해 넣고 계산 근거를 주석 한 줄로.
   - PRD가 정하지 않은 입력이 필요하면 결과를 바꾸지 않는 값을 고르고 `// 가정: …` 주석을 남긴다.
3. **이름**: 기존 테스트처럼 한국어 문장 + 끝에 검증 번호. 예: `it('높이가 1cm 넘치면 두 방향 모두 안 들어가요 (AC64)', …)`. 계획에 영어 테스트 이름이 있으면 그 뜻을 그대로 한국어로 쓰고, 계획 이름은 `describe` 위 주석에 남겨 리뷰어가 대응을 찾게 한다.
4. **위치·도구**: 로직은 `src/logic/*.test.ts`, 화면은 `src/App.*.test.tsx`(Testing Library, 사용자가 보는 이름으로 찾기), 서버는 `worker/test/*.test.ts`(첫 줄 `// @vitest-environment node`). 가짜 전역은 `src/test/aiMocks.ts`에만 두고 `afterEach`에서 되돌린다.
5. **실패 확인**: 새 동작은 구현 전에 돌려 실패를 본다. "모듈 없음"은 시작일 뿐이라, 함수 껍데기(빈 배열·잘못된 값을 돌려주는)를 둔 뒤 **기대값 불일치로** 실패하는 것까지 본다. 이미 있는 구현이 그 사례를 만족해 처음부터 통과하는 것은 괜찮다(회귀 방지 테스트) — 그때는 단언을 잠깐 틀리게 바꿔 실패하는지 한 번 확인한다.
6. **명세 충돌**: PRD 문장과 계획이 다르거나 PRD가 비어 있으면 임의 기대값으로 메우지 않는다. PRD를 따르고, 정할 수 없으면 updating-prd로 질문을 남긴다.
7. **기존 테스트**: 바꾸지 않는 것이 기본이다. 명세가 바뀌어 기존 기대값이 틀려졌을 때만 PRD 변경(updating-prd)과 함께 고치고, 바꾼 이유를 커밋 메시지에 적고 전체 테스트로 회귀를 확인한다.

## 자주 하는 실수

- 구현을 먼저 쓰고 출력값을 기대값에 붙여 넣는다 → 버그가 기대값이 된다.
- PRD가 일부 줄만 적은 결과를 전체 배열 `toEqual`로 단언하면서 나머지 줄을 지어낸다 → 적힌 줄만 `[n]`으로 단언하거나 나머지는 기능 절의 규칙에서 끌어온다. 부분 단언이어도 명세가 정한 줄 수·순서·"없어야 할 줄"(예: 방향 2 설명이 없음)은 확인한다.
- 화면 테스트에서 클래스 이름이나 DOM 구조로 찾는다 → 역할·이름(`getByRole('button', { name: '확인하고 저장' })`)으로 찾는다.
